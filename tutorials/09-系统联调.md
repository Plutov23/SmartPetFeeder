# 第 9 章：系统联调与完整运行流程

## 本章目标

完成本章后，你应该能够：

- 按层次组合所有模块
- 保存一份可复现的启动日志
- 验证传感上报、手动出粮、定时出粮、视觉记录和视频
- 根据数据路径定位故障所在层
- 完成项目的端到端验收

## 1. 不要一次接通所有功能

联调不是“全部接上看看能不能运行”，而是逐层确认：

~~~text
电源与主控
  ↓
本地传感器和执行器
  ↓
ESP-01S 与 OneNET
  ↓
MaixCam UART
  ↓
小程序 API
  ↓
小程序视频
~~~

只有当前层稳定后，才增加下一层。出现问题时退回最近一个通过的状态。

## 2. 联调前检查

### 电源

- STM32 电压正常
- ESP-01S 发送时电压不跌落
- 电机使用合适的驱动和电源
- 所有通信模块共地
- 没有发热、异味或短路

### 配置

- <code>app_config.h</code> 已填写
- <code>vision/maixcam/config.py</code> 已填写
- <code>miniapp/wechat/config.js</code> 已填写
- 三个本地配置文件都未被 Git 跟踪

### 标定

- HX711 已去皮并标定
- 每克步数已经实测
- 手动与定时出粮系数一致
- OLED 最大粮量与实际粮仓一致
- DS1302 时间正确

### 平台

- OneNET 设备在线
- 物模型字段和类型正确
- API Authorization 可用
- MaixCam 与手机在同一局域网

## 3. 推荐上电顺序

1. 接通路由器或热点。
2. 启动 OneNET 调试页面。
3. 启动 MaixCam，等待获得 IP、模型加载和 WebSocket 就绪。
4. 接通 STM32 和传感器电源。
5. 打开 USART1 日志。
6. 等待 ESP-01S 初始化完成。
7. 打开微信小程序。
8. 最后接入或启用电机负载。

保留完整日志，不要只截取错误发生后的几行。

## 4. 启动日志检查点

启动过程应按顺序经过：

| 阶段 | 关键现象 |
| --- | --- |
| 主控 | Board power on |
| 计划 | Schedule module initialized |
| HX711 | 去皮开始、零点完成 |
| Wi-Fi | 热点连接结果 |
| MQTT | 初始化步骤完成 |
| MaixCam | USART2 开始接收 |
| 主循环 | RTC、重量、温湿度持续更新 |

如果日志停在某个阶段，优先排查下一条尚未出现的模块。

## 5. 测试一：本地传感和显示

先断开网络影响，确认：

1. DS1302 每秒递增。
2. HX711 空载接近 0 g。
3. 放置已知重量后读数合理。
4. OLED 显示时间和余粮比例。
5. AHT20 每 5 秒返回温湿度。
6. 电机不运行时数值稳定。

通过标准：连续运行 10 分钟，无复位、无卡死、无明显漂移。

## 6. 测试二：云端上报

数据路径：

~~~text
AHT20/HX711
  → STM32
  → USART3
  → ESP-01S
  → MQTT
  → OneNET
  → 小程序 HTTPS
~~~

验证：

- USART1 每 5 秒出现 Cloud Sync
- OneNET 属性值更新
- 小程序最多一个轮询周期后更新
- 改变重量后三个位置的值方向一致

如果 STM32 日志正确而 OneNET 不更新，问题在 ESP/MQTT/平台层；如果 OneNET 正确而页面不更新，问题在 API/小程序层。

## 7. 测试三：手动出粮

使用最小的 5 g 测试：

1. 小程序点击试出粮。
2. 开发者工具确认 API 返回。
3. OneNET 确认属性下发。
4. USART1 出现 Manual feed。
5. 蜂鸣器提示。
6. 电机按正确方向转动。
7. 称量实际出粮。
8. 重复至少 5 次。

记录平均值、最大值、最小值和失败次数。请求成功但实际未出粮也应记为失败。

## 8. 测试四：定时出粮

1. 将 DS1302 校准到当前时间。
2. 新建一个未来 2 分钟的计划。
3. 确认 USART1 出现 Schedule updated。
4. 等待时间匹配。
5. 确认同一分钟只触发一次。
6. 确认出粮方向和重量。
7. 关闭计划并确认不会再次执行。
8. 重启 STM32，验证计划丢失这一当前限制。

定时测试期间不要反复修改 RTC，否则难以判断重复触发逻辑。

## 9. 测试五：视觉健康记录

先用串口工具模拟：

~~~text
CAT,EATING
CAT,EATING
NONE,NONE
~~~

两类事件间隔应超过 5 秒。确认：

- 只在第一次 EATING 开始计时
- NONE 结束计时
- 计算消耗重量
- <code>eat_cnt</code> 增加
- OneNET 出现健康属性
- 小程序生成一条新记录

再使用真实 MaixCam 重复测试。模拟通过而真实失败时，应集中排查模型、机位、阈值和 UART。

## 10. 测试六：视频链路

路径：

~~~text
MaixCam 摄像头
  → JPEG
  → Base64 JSON
  → 局域网 WebSocket
  → 微信小程序
~~~

确认：

- 小程序画面持续更新
- 标签随目标变化
- 断开 Wi-Fi 后页面能显示掉线
- 恢复网络后手动重连有效
- 视频断开不影响 STM32 本地喂食

## 11. 完整验收矩阵

| 功能 | 操作 | 预期结果 | 证据 |
| --- | --- | --- | --- |
| 称重 | 放置已知砝码 | 误差在目标范围 | 日志与照片 |
| 温湿度 | 改变环境 | 数值方向合理 | 日志与云端 |
| 手动出粮 | 下发 5/20/50 g | 电机动作、重量可接受 | 视频与记录 |
| 定时出粮 | 设置未来时间 | 准时且只执行一次 | 日志 |
| 视觉状态 | 宠物靠近食盆 | UART 状态变化 | 两端日志 |

| 视频 | 打开实时页 | 画面连续 | 录屏 |

| 重启恢复 | 重启设备 | 已知状态符合设计 | 检查表 |

## 13. 时序和阻塞风险

当前系统存在若干阻塞操作：

- ESP 初始化固定等待
- AHT20 测量等待 75 ms
- HX711 等待 DOUT 没有超时
- 蜂鸣器使用 <code>HAL_Delay</code>
- MQTT 发送包含短延时

联调时如果 UART 丢帧或界面停顿，应同时检查阻塞调用，而不是只增加缓冲区。

## 14. 故障隔离方法

### 小程序没有温度

按顺序确认：

~~~text
AHT20 日志
  → Cloud Sync 日志
  → OneNET 属性
  → HTTPS 返回
  → 小程序字段映射
~~~

### 点击出粮没有动作

按相反方向追踪：

~~~text
小程序请求
  → OneNET 下发
  → ESP USART3
  → STM32 解析
  → 步数计算
  → 电机驱动
  → 机械出粮
~~~

每次只验证一个边界，就能确定问题落在哪一层。
