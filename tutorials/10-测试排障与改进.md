# 第 10 章：测试、排障与改进方向

## 本章目标

完成本章后，你应该能够：

- 使用统一方法定位跨模块故障
- 为传感器、执行器、网络和视觉设计测试
- 区分偶发故障、稳定复现故障和设计限制
- 为项目建立可执行的改进优先级
- 提交别人能够复现的 Issue
- 完成开源教程阶段的最终验收

## 1. 排障的基本顺序

遇到问题时按以下顺序：

1. 先断开危险负载
2. 检查电源和温度
3. 记录完整现象
4. 找到最后一个正常边界
5. 单独验证故障模块
6. 每次只改变一个变量
7. 保存日志和结果
8. 修复后做回归测试

不要同时改接线、代码、供电和参数。那样即使问题消失，也无法知道真正原因。

## 2. 四层定位模型

| 层级 | 典型问题 |
| --- | --- |
| 电气层 | 电压、共地、线序、干扰、过流 |
| 驱动层 | GPIO、I2C、UART、定时器、超时 |
| 协议层 | 波特率、主题、JSON、字段、帧边界 |
| 业务层 | 标定、计划、去重、状态转换、权限 |

例如“远程出粮失败”可能分别是：

- 电机供电不足
- TIM3 没启动
- MQTT 下发没有到达
- <code>feed_amount</code> 解析为 0

先确定层级，再查看对应源码。

## 3. 电源与复位问题

### 现象

- 电机一转 STM32 就重启
- ESP-01S 联网时反复重启
- OLED 突然花屏
- HX711 在电机运行时跳动

### 检查

- 测量静态和负载瞬间电压
- 检查所有 GND
- 缩短大电流供电线
- 将电机与逻辑电源分开
- 检查驱动和电源额定能力
- 在模块附近增加合适去耦
- 检查是否存在反接或短路

只看万用表静态电压可能看不到瞬时跌落，必要时使用示波器。

## 4. STM32 没有日志

按顺序检查：

1. 固件是否成功烧录
2. STM32 是否正常复位
3. 外部 8 MHz 晶振是否工作
4. USART1 是否使用 PA9/PA10
5. USB 转串口是否与主控共地
6. 终端是否为 9600、8N1、无流控
7. TX/RX 是否交叉
8. 程序是否进入 <code>Error_Handler()</code>

使用调试器在 <code>main()</code>、<code>SystemClock_Config()</code> 和第一条日志附近设置断点，可以区分时钟故障和串口故障。

## 5. HX711 故障

| 现象 | 优先检查 |
| --- | --- |
| 初始化卡死 | 供电、PA11 DOUT、PA12 SCK、共地 |
| 一直为 0 | 比例方向、去皮状态、受力结构 |
| 比例错误 | 重新使用已知砝码计算系数 |
| 随机跳动 | 机械固定、电源、电机干扰、滤波 |
| 长期漂移 | 预热、温度、结构回弹、零点 |

回归测试至少包含空载、轻载、标定点和实际最大常用重量。

## 6. 电机与出粮故障

| 现象 | 优先检查 |
| --- | --- |
| 只抖不转 | IN1 到 IN4 线序、速度、供电 |
| 方向错误 | 软件方向或驱动线序 |
| 少出粮 | 失步、堵塞、参数绝对值偏小 |
| 重复性差 | 粮粒差异、架桥、叶轮间隙 |
| 停止后发热 | 线圈未释放、堵转、驱动异常 |

测试不能只看电机是否转动，应称量实际出粮并统计多次结果。

建议记录：

- 目标重量
- 实际重量
- 误差
- 电机步数
- 粮仓余量
- 是否卡粮
- 供电电压

## 7. I2C、OLED 与 RTC 故障

### AHT20

- 扫描或确认 7 位地址
- 检查 PB8/PB9 和上拉
- 区分 HAL 地址 <code>0x70</code> 与 7 位地址 <code>0x38</code>
- 观察成功和失败日志

### OLED

- 确认 PB13/PB14
- 确认软件 I2C 驱动与模块控制器兼容
- 检查供电和刷新时干扰

### DS1302

- 当前实际接线为 PA6 RST、PA4 CLK、PA5 IO
- 确认后备电池
- 确认一次性设置时间代码已经重新注释
- 断电后验证持续计时

## 8. ESP-01S 与 OneNET 故障

从低到高检查：

~~~text
AT
  → Wi-Fi
  → IP
  → MQTT 指令支持
  → OneNET 在线
  → 属性上报
  → 属性下发
  → 设置回复
~~~

保留 ESP 原始响应非常重要。只有 STM32 的“已发送”日志，不能证明服务器已接受数据。

常见原因：

- 3.3 V 供电不足
- 只支持 5 GHz 的热点
- MQTT AT 固件不兼容
- 三个设备参数不属于同一设备
- Token 过期
- 物模型字段或类型错误
- 下发响应被换行拆分

## 9. MaixCam 故障

分三条链路检查：

### 图像链路

摄像头是否能抓图、显示和压缩。

### 推理链路

模型是否加载、类别编号是否正确、目标是否达到置信度阈值。

### 通信链路

UART 是否每秒发送正确文本，WebSocket 是否发送有效 JSON。

先用录制画面或固定目标验证模型，再接入 UART；先用串口工具模拟协议，再接真实 MaixCam。

## 10. 小程序故障

打开开发者工具的 Console 和 Network，分别检查：

- JavaScript 异常
- HTTPS 状态码
- OneNET 业务返回码
- 请求参数
- WebSocket 连接状态
- 收到的 JSON 内容
- 本地缓存

如果 OneNET 控制台数据正确而页面为 0，问题通常位于请求授权、字段映射或页面状态更新。

## 11. 稳定性测试

功能通过后继续测试：

### 连续运行

- 至少运行数小时
- 观察内存、日志频率、温度和复位
- 记录 Wi-Fi 和 WebSocket 断开次数

### 重复出粮

- 连续执行多次小、中、大重量
- 统计平均误差、标准差和失败率
- 检查粮仓从满到低余量时的变化

### 断网恢复

- 关闭并恢复热点
- 重启路由器
- 改变 MaixCam IP
- 确认系统能恢复或给出明确故障状态

### 异常输入

- 0 g
- 负数
- 超大重量
- 非法计划编号
- 非法时间
- 超长 UART 帧

当前代码未对所有异常输入做完整校验，测试时应断开真实机械负载或限制电源。

## 12. 当前项目已知限制

### 固件

- HX711 等待没有超时
- 运行时称重没有滤波
- 手动与定时出粮系数定义分散
- 计划只保存在 RAM
- 命令参数校验不完整
- 多处使用阻塞延时

### 网络

- MQTT 连接结果没有完整状态机
- 下发数据使用字符串搜索解析
- 默认端口和安全配置适合演示，不等于生产安全
- 断网自动恢复能力有限

### 视觉

- 使用框比例和位置推断行为
- 没有多帧防抖和置信状态
- 只处理第一个目标
- WebSocket 没有鉴权
- Base64 视频效率较低

### 小程序

- 高权限平台凭据位于前端
- 历史记录只保存在本机
- 设备重启后的计划没有自动恢复
- 局域网 IP 需要手工配置

## 13. 改进优先级

### P0：安全与失控保护

1. 限制单次和每日最大出粮量
2. 增加电机超时、堵转或异常停止
3. 给 HX711 增加读取超时
4. 后端保存 OneNET 凭据并鉴权
5. 增加设备离线和传感器异常状态

### P1：可靠性

1. 统一所有可配置参数
2. 将计划和标定参数保存到 Flash
3. 增加 Wi-Fi/MQTT 重连状态机
4. 使用可靠 JSON 解析
5. 增加称重中值和滑动平均
6. 视觉状态增加连续多帧确认

### P2：体验与扩展

1. 自动发现 MaixCam 地址
2. 使用云数据库同步历史记录
3. 增加 OTA 或版本管理
4. 增加多宠物识别
5. 使用更高效的视频协议
6. 增加校准向导和设备诊断页面

## 14. 如何提交可复现的 Issue

Issue 至少包含：

~~~text
问题标题
使用的教程章节
Git 提交号或 Release 版本
开发板和模块型号
供电方式和实测电压
接线说明
完整复现步骤
预期结果
实际结果
USART1 日志
ESP 或 MaixCam 日志
截图或短视频
已经尝试的排查步骤
~~~

提交前隐藏：

- Wi-Fi 名称和密码
- OneNET Token 与 Authorization
- 正式 AppID 和用户信息
- 局域网公网映射地址
- 其他个人信息

## 15. 毕业设计演示建议

演示前准备：

- 一个稳定的独立热点
- 已充电的备用电源
- 少量统一规格宠物粮
- USB 转串口和完整日志
- 一段离线备用演示视频
- 打印的系统架构图
- 已知限制和改进路线

推荐演示顺序：

1. 介绍问题和系统架构
2. 展示本地传感和 OLED
3. 展示手动出粮
4. 展示定时计划
5. 展示视觉状态和视频
6. 展示健康记录
7. 主动说明当前限制
8. 介绍开源仓库和复现教程

主动说明边界比掩盖问题更能体现工程判断。
